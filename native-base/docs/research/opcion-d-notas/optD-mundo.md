## 1. SERVER = MMO server kept intact; multi-user broadcast machinery

### 1.1 Server is a "controller-authoritative" relay (BSM §Resumen, §1) [STATIC]
- Server does NOT simulate players. Move/StartAction/Rotate/ChangeAIState Acks are written ONLY from the Req handlers. No timer/tick broadcasts transforms (85 timers, none transform). Player (actor type 1) excluded from server tick.
- Each actor has a controlling client (player, or for NPCs the client running their AI: ChangeAIStateReq, AITeleportReq are C>S). Server relays controller's data to `ToNearExceptOneControl`.
- => Option D: guest client must be the controller of its own player on the host server; NPC AI is CLIENT-simulated → decide which client controls each NPC (ownership). [STATIC]
- In single player the broadcast writers RUN but "Near" has no other sessions → writer exits before serializing (AEC §Resumen 1). E.g. UpdateWallUpDataReq handler with one session sends nothing (BSM §10.2). [STATIC]

## 2. CLIENT side: dispatch, actor creation, "the only user" assumptions

### 2.1 Troc framing and dispatch (ICC §1; MAF §Reglas; MRC §1; C2) [STATIC + LIVE]
- Wire frame: `u16 opcode | u8 slot | u16 payload_len | payload` (5-byte header). Slot 0 normal; mod injects with slot 0 or 0xFF (both accepted [LIVE]).
- Hooks: `ClientNet::PostPacket` exe+0x35C670 (C>S), `ClientNet::OnRecvPacket` exe+0x35CA00 (S>C). Mod uses mid-hooks there; injection = call OnRecvPacket original with own bytes from inside the hook, on the client NET thread, under SEH (C2 §hito 4c; E4C) [LIVE].
- Flow: OnRecvPacket 0x35CA00 → queue → main thread 0x35D0C0 → Ack vf2 (MRC §1). ClientNet::ProcessRecvQueue retry path at 0x35D1BD; retry queue at ClientNet+0xF0 (MAF §Reglas 3).
- Troc table: Acks Move/Rotate/StartAction/ChangeAIState mask 1, flags 0x200, default vf1 0xB54130, size 5..32710 (MAF).
- 1,116 TrocTr* message types: 486 Req, 525 Ack (HV). Opcode CSV: `troc_messages_2976.csv` (PCR §4).
- Handler validation: `p->size-5 == *(u16*)(pkt+3)`; DeserializerMemory (vtable 0x5721C60, Read 0x141F270, cursor +0x1C) must consume EXACTLY payload_len else returns `[0x6CDB970]` (silent drop). Return codes: 0 applied, `[0x6CDB970]` bad format, `[0x6CDB9D0]` retry (MAF §Reglas, §verificar).
- Actor lookup for Ack vf2: mgr = `[[exe+0x6D69188]+0x38]` (+0x08 container, +0x10 RW lock); 0x8A67E0 → 0x8B3C00 → 0x464290(container,key). Missing actor → OnRecvPacket sets ctx+0x50=0, Ack does nothing. **No "if key == my player return" check** in these handlers (MAF §Reglas 2).

## 4. TRANSPORT: in-process client↔server and the mod's network

### 4.1 In-process Troc loopback [STATIC + LIVE observations]
- C2 §Arranque: first C>S packet opcode **1001** (not in Troc table) = connection handshake, payload contains ASCII "127.0.0.1"; server replies **ConnectToServerAck 1002**. "Entry point of the MMO login." Login later: LoginCharacterToFieldServerReq (carries characterNo 0x7FFF…), LogoutCharacterToFieldServerAck (relogin). - ClientNet: PostPacket 0x35C670 (C>S; any thread that sends), OnRecvPacket 0x35CA00 (S>C; runs on client "NetworkThread"), main-thread consumer 0x35D0C0, ProcessRecvQueue retry at 0x35D1BD, retry queue ClientNet+0xF0, byte ClientNet+0x112 = "connected" flag (BSM §10.2). S>C injection: `g_queue` drained inside OnRecvPacket hook (whole due queue at once; bursts of 722 packets after menu) (PR §2.4).
- Loading: GameLoadingStartReq 2437 → LoadingCompleteReq 2445 (byte 01 save load, 00 fast travel/respawn) + LoadingCompleteAck 2762; server removes all NPCs with RemoveActorAck reason 19 (PR §2.1). ## 5. CLOCK / TIME (MRC §2; PCC; hora-del-dia.md §1.2; BSM §7.7) [STATIC + capture]
- Client "now" = 0x1416B80() + [exe+0x6D69438]. 0x1416B80: on client main thread = frame-cached ms `[0x146C8CD68] + [0x146C8CD70]/1e6` (if [0x146C8CD35]==0); on server thread = (clock_ns − [0x146EFBC70]) / 1e6 (real clock). Both ms since a process epoch.
- **TLS flag `gs:[0x58] → [+0x1EC] != 0` = SERVER thread** (hora-del-dia.md §1.2): selects server vs client copies of globals (FieldTime client 0x146A6D218 / server 0x146A6D238; icon cfg 0x6D69528 vs 0x6D69530; clock bias not added on server thread). → Server and client in-process are distinguished per-thread, NOT per-object. Option D implication: a second client cannot simply run in the same process; but a REMOTE client talking to host server only needs the host's server thread. [STATIC, confirm live]
- [exe+0x6D69438] (i64) = client→server offset ms, written by ServerTimeInfoAck handler 0xBDF310: offset = server_tick − client_now. [0x146D69430] = unix_server − time().
- ServerTimeInfoAck 2188 (S>C, every 5 s wall, 20 B: u32 0 | u64 server tick ms | u64 unix seconds); triggered by server timer ServerTimeInfoRepeatTimer 1022 (server handler 0x2C37200) (troc_messages_2976.csv). Same clock that stamps Req ts (Time 3362494 ↔ MoveActorReq ts=3362494) [capture].
- **Pause**: opening menu/inventory/map STOPS the game clock (ServerTimeInfoAck keeps arriving every 5 s but its ms value doesn't advance; no Reqs sent). After the pause, Reqs continue from the frozen value → each PC's game clock loses the pause duration vs the other (PCC §1.1) [capture, two PCs]. Hitches lose time too (−0.92 s seen).
- Remote actor buffer rejects ts ≤ last; T=now−200; >1000 ms gap → reset; so cross-PC timestamps MUST be re-stamped into the receiver's clock (mod uses ClockMapper + `ts += g_ts_shift`; Move +0xD5, StartAction Ack +0x160, Rotate +0x9C). Recommended fix: resample receiver's real clock inside OnRecvPacket, clamp ts to [now−500, now+300], strict monotonic per actor/buffer, don't inject movement while locally paused (PCC §4 F1–F4).
- Server-side timestamps embedded in data: VaryHPAck +0x30 (server ms), buff/skill lists in ActorLoadDataAck (server ms). In Option D the guest would receive host-server timestamps directly; the guest client's offset [exe+0x6D69438] is set from ServerTimeInfoAck, so if host's server sends ServerTimeInfoAck to the guest, the guest client's clock would align automatically [ASSUME]. But PAUSE: host pausing stops the host's server clock (and in SP the server probably pauses) → would freeze the guest's world [ASSUME; key risk].
- FieldTime/time-of-day: SetFieldTimeReq 2125 (36 B) / SetFieldTimeAck 2816 (35 B: u32 actor key | FieldTime 31 B); anchor in local server timebase; can't be copied raw between PCs (hora-del-dia.md).

## 7. OPEN QUESTIONS / DEAD ENDS / RISKS for Option D
1. **Session layer**: how ClientNet connects (opcode 1001 handshake w/ "127.0.0.1", ConnectToServerAck 1002) and how the server creates per-user sessions — documented in troc-sintesis.md / troc-dispatch.md / segunda-sesion.md (not in this read set; segunda-sesion.md shows login sequence: ServerTimeInfoAck, MainUserDataStartAck (0x90100000), CharacterLobbyDataAck ("Kliff"), MainUserDataEndAck; and a server dispatch tree with 0x2A1E9D0 ServerTimeInfoAck [S]). MUST read those.
2. SAM quotas: users N, players 100·N (PRK §1.3) — N value unknown; if N=1, a second ServerUserActor allocation may fail (eErrNoInvalidActorKey or quota). Check param+0x80..0x98 & N live.
3. Server ownership checks: MoveActorReq/RotateActorReq require session's ServerUserActor vf170() == actor+0x90 → guest Reqs must arrive on a session bound to the guest's ServerUserActor (BSM §1.1).
4. NPC/AI authority: in SP the client simulates ALL world NPCs (mode 3, actor+0x90 = local user; MoveActorReq for 3,393 actors). With two clients, both would simulate the same NPCs unless the server assigns control (ChangeAiControlAck, OverriedOwnershipStateTypeyAck exist as message names — CGI §4.2) — unexplored. Server relays ChangeAIStateAck to ExceptOneControl (so MMO had one controller per NPC).
5. Dead relays: ExceptOneControl/ExceptOneSelf writers bail out before serializing when no other session is "near" — with a real second session they should serialize. AOI ("Near") via field interest node TS+0x540 / sector; the guest's session must be registered in the field/sector interest lists (0x4A2010 session list) — mechanism not analyzed.
6. Features that the SP build removed/left dead: UpdateWallUpDataReq emitter gated by never-written bool exe+0x6D76D5C (set it on the guest's client or relay manually); UpdateVisiblePlayerAck 2135 has no server writer; minimap "other player" icon path absent (requires mercenary-clan membership); ChangeRideSeatAck client stub; no server snapshot. RideOnVehicleReq never sent (mount = interaction).
7. Client-side single-user assumptions: actor+0x96 "local character" mark (set only at 0x46B271); characterNo lookup returns FIRST matching actor (0x8AEB30) → EquipSlotListCache conflicts if two players share characterNo (both PCs use same save → same characterNo 0x7FFFFFFFFFFFFFFF!) [LIVE bug]; sensor D only for local char; UpdateSelfDestinationAck no null check; pins require local actor.
8. Both PCs' saves: characterNo 0x7FFFFFFFFFFFFFFF is the SP constant; item instance numbers (itemNo) identical between saves of the same game → collisions in any server-side table keyed by characterNo/itemNo if the host server loads a second character [ASSUME, high risk].
9. Horse/mount remote crash class (null action layer) — host will see the guest's horse as a mode-2 remote mount; need the restore byte [[CC+0x40]+0x30] / first action (ICC §11).
10. Group login: actors with parent/children log in as groups; remote party ids per-world (CGI).
11. Pause: SP pauses the game clock in menus (PCC) — in Option D, the host's server clock would stop when host opens a menu (and guest would freeze), and the guest's own menu presumably pauses only its client [ASSUME].
12. Save safety: server components write the save (ServerContentsMiscActorComponent slot10 0x28B7360 SQL/reflection). A second ServerUserActor on host might be written into host's save or attempt DB writes for guest character [ASSUME, high risk]. Rule: backups before any write test; never save with copies present.
13. Crash reporting: crashes go to Pearl Abyss (sentry/crashpad); all reads guarded; hooks only at function starts or safetyhook mid-hooks.
14. Thread affinity: inject S>C from inside OnRecvPacket hook (client NetworkThread); C>S published inside a real PostPacket; server hooks run on server thread; TLS +0x1EC distinguishes server thread.
15. Key translation between PCs: world keys 0xB01… are per-world counters; horse always 0xB0100003 only on first login; party ids per world. Option D removes this problem (single key space on host) — biggest structural win.
