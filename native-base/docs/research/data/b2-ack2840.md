# B2: why `ConnectCryptogramToServerAck` 2840 never reached session 2

Build 1.0.0.2976, base `0x140000000`, RVAs. Static only (capstone; scripts in
`%TEMP%\claude\b2\`). **[E]** = read in the disassembly, **[S]** = inference.

## 0. Answer (short)

**The Req never reached its handler.** 2319 is a *deferred* Troc. `OnRecvPacket` queues it in
`ServerNet+0x38` under the key `*(u32*)[session+0x88]`, because the session has no user. The mod
writes **2** there. Any nonzero key whose bits 28-29 are 0 goes to table 0 of that queue, and
**table 0 has exactly N = 1 entry** (N = `param+0x40` = 1 in single player, see D0 §1.1).
Index 2 is read **past the end of a 16-byte array, with no bounds check**. The value read was
null (the game did not crash), so the push returns error `[0x6CDB9E8]`. `OnRecvPacket` then frees
the packet copy **without logging anything**. So no vf2, no `0x2C492A0` and no Ack. Session 1 at
boot has id **0**, and key 0 goes to the common FIFO, which works.

**Fix:** set `*(u32*)[session2+0x88] = 0` (do not write 2). Section 5 has the details.

## 1. Path of the Req up to the drop [E]

| RVA | Code | Meaning |
|---|---|---|
| `0x2774033` | `cmp dword [r13+0x1C],1` / `jne` | Troc+0x1C == 1: deferred (2319 is) |
| `0x2774041` | `call 0x1439060` | new `TrBufferPoolValue` |
| `0x277405D` | `mov [rax+0x48], r15` | value+0x48 = session (r8 = our session 2) |
| `0x2774061`-`0x2774092` | `test rbx,rbx` (user) … `mov rax,[r15+0x88]; mov eax,[rax]; mov [r14+0x54],eax` … `mov [r14+0x58],eax` | no user: **key = +0x54 = +0x58 = `*(u32*)[s+0x88]`** |
| `0x27740BB`-`0x27740CF` | `r9d=[r14+0x58]; rcx=[ServerNet+0x38]; call 0x143A580` | push(queue, &res, &value, key) |
| `0x27740EC`-`0x2774121` | `cmp eax,[0x6CDB9E8]; jne` → `call 0x1438E70` (value dtor) → `0x47F02BC/03BC` free | **error ⇒ the packet is freed silently** (no log call in this block) |

`0x143A580` = the push [E]:
```
143A5A1  test r9d,r9d ; je 143A609         key 0 -> common FIFO only (Q+0x30)
143A5B2  mov eax,ebx ; shr eax,0x1C ; test al,3 ; mov eax,0x40 ; mov ecx,0x38 ; cmove eax,ecx
143A5C6  mov rax,[rax+rdi]                 table = Q+0x38 if ((key>>28)&3)==0, else Q+0x40
143A5CA  and ecx,0xFFFFF ; add rcx,rcx ; mov rax,[rax] ; mov rcx,[rax+rcx*8]   entry = data[idx*16]  (NO bound check)
143A5DC  test rcx,rcx ; jne 143A5F7
143A5E1  mov eax,[0x6CDB9E8] ; mov [rsi],eax ; ... ret         null subqueue -> error
143A5F7  call 0x143AB10 (push to the per-key subqueue), then falls into 143A609 (push {key,value} to the common FIFO)
```
How the tables are built [E]:
- `ServerNet::Start` `0x2772355`-`0x2772368`:
  `r8=[ServerNet+0x88]; r9d=[r8+0x44]; r8d=[r8+0x40]; call 0x143A0F0`. So table 0 gets
  `param+0x40` = N = 1 entries and table 1 gets `param+0x44` = 15 501.
- `0x143A0F0` → `0x143A371` `0x143AD60(Q+0x38, &res, N)`. `0x143AD60` allocates `N<<4` bytes
  (`0x143AD82` `shl ecx,4`), stores `count = N` (`0x143ADE3`) and fills `{0, -1}`.
- Loop `0x143A380`-`0x143A42F`: one subqueue (0x78 B, ctor `0x143AF40`) **per table-0 entry,
  so 1**.
- Table 1 (`0x143A4BF`) is left empty. `0x2A837E0(SAM, key)` fills it lazily for each actor key
  that `CreateUser` reserves. It uses the same class/index formula (`0x2A83806`-`0x2A838BC`).

Key 2 means table 0, index 2, read at `data+0x20` in a 16-byte block. That is out of bounds. With
no crash, it read 0 [S: the heap contents cannot be proven statically. A nonzero value would have
been used as a subqueue object: `0x143AB2D call [rax+8]`, which means a crash or a lock on a
foreign object].

Session 1 [E-x]: `ServerModule::Init` (`.xtls 0x100B82BF`-`0x100B82FC`, readable) does
`xor edx,edx; call 0x1436EE0`, then sets vtables, `+0xB0/+0xB8/+0xC0`, `+0xC8` and `+0x18 = '1'`.
**It never writes `[[s+0x88]]`**. The ctor allocates the u32 and leaves it at **0**
(`0x1436F1A`, plus the 4-byte block at `0x1437104`-`0x143714D`: `mov [rbx], r12d`). So the boot
2319 (no user) went to key 0, the common FIFO [S strong; one live read of `*(u32*)[s1+0x88]` would
make it E].

The executor would also reject a mismatch [E]: `0x2774730` (no-user branch `0x27748BD`):
```
27748C6 mov rcx,[rsi+0x88] ; mov eax,[rdx+0x54] ; cmp [rcx],eax ; jne 2774A80   id changed -> drop
27748D8 cmp [rsi+0x90],rbx(0) ; je 27749CB                                        no user -> ExecuteTroc(actor=0, session=value+0x48)
2774A08 call 0x2774B20 (troc->vf2) ; on res!=0 and !session->vf(0x30) -> session->vf(0x18)
```

## 2. How the Ack's target is chosen [E] (Q1)

The target is **the session pointer from `TrocParams+8`**. It does not come from `+0x88`, `+0x90`,
a global or the user key.
- vf2 `0x2A21670`: `0x2A219C7` `mov rdx,[r13+8]` (TrocParams+8 = session) →
  `call 0x2C492A0(&res, session, &bytes, &out)`.
- `0x2C492A0`:
  - `0x2C492BE` `rdi = session`;
  - `0x2C493B2`-`0x2C493CF` builds a finder on the stack: vtable `0x5B25438` (ToTarget), and
    `[rsp+0x50] = rdi` (finder+0x10 = session);
  - `0x2C49408` `call 0x2A1F680`.
- `0x2A1F680` (writer of 2840: `0x2A1FAEA` `mov ecx,0xB18`):
  - `0x2A1F6E6` `finder->vf1(TLS vec)`. ToTarget vf1 `0x2A757F0` pushes `[finder+0x10]` if it is
    non-null (`0x2A757FA`, `0x2A7583D`). Count = 1.
  - `0x2A1F6F1` count == 0 → return. **The only "no target" exit, and it cannot happen here.**
  - `0x2A1F6FA` `0x2961CA0(finder)`: is there an open ScopeSender on this thread
    (TLS `[+0x250]+0x2AC/+0x298`) with the same finder (vf `0x10` = `0x2A75850`, compares
    `+0x10`)? If so, it appends there (`0x2A1F716`-`0x2A1F87C`) and the send is the scope's flush
    [S].
  - Otherwise: `0x2A1F8DF` `0x2771B30` allocates the `AsyncRequestSend` (alloc fail → log
    `0x35D8D0` at `0x2A1FC7D`) and the payload is serialised.
  - `0x2A1FB00` count == 1: `rsi = vec[0]` = session.
  - `0x2A1FB1F` `session->vf(0x70)()`: the result is ignored.
  - `0x2A1FB22`-`0x2A1FB4D` `crypto=[s+0x98]`; if `crypto->vf(0x10)()==1`, encrypt (`vf 0x28`).
  - `0x2A1FB50`-`0x2A1FBB6` frame (`size<1` or `> cap` → no frame).
  - **`0x2A1FBD4` `call [rax+0x48]` = vf9 Send** (`0x1437740`, our `session2_send`).
  - count > 1 → `0x2A1FC02` `ServerNet::SendPacket 0x2773870`.

## 3. Conditions that could drop the Ack for session 2 (Q2) [E]

| Where | Condition | Session 2 |
|---|---|---|
| `0x2773E3E`/`0x2773EDF`-`0x2773EF0` | no user: only Troc `flags_16 & 1` (2319 = 0xFF) | passes |
| **`0x27740CF`→`0x143A5DC`** | **key `*(s+0x88)` must be 0 or an existing subqueue** | **FAILS with 2** |
| `0x27748D0` | executor: `*(s+0x88)` unchanged since the push | ok |
| `0x2A216C5` | `Troc+0x21 != 0` → handler off (`*res=0`) | same for s1 |
| `0x2A216A3`-`0x2A216BF` | `size-5 == u16 len`, ≤ 0x7FC1 | ok (packet passed before) |
| `0x2A21798`-`0x2A21808` | wstring len ≤ 0x100 and terminated by `u16 0` | "TEMP" ok |
| `0x2A218EF` | all bytes consumed | ok |
| `0x2A219B9` | type byte == 4 | ok |
| `0x2C492E7` | DER decode `0x4063250` returns 0 → error `[0x6CDB9B0]` | captured DER is valid |
| `0x2C49330`/`0x2C49348` | RNG `0x4059080` (32 B key, 12 B IV) != 1 → error | not session-dependent |
| `0x2C49376` | RSA encrypt `0x4063340` == -1 → error | not session-dependent |
| `0x2C492C4`/`0x2C492E1` | writes `[[s+0xA0]]`: needs `+0xA0` non-null | the ctor creates it (`{0,0,2}`) |

- **vf(0x70)** (slot 14) = `0x3600C0` `mov al,1`.
  - In `0x2C49413` it only decides that **no** key is installed in the crypto (`vf 0x38`).
  - In `0x2A1FB1F` its result is ignored.
- **vf(0x58)** (slot 11) = `0x35EA90` → `.xtls 0x86F0570` (a stub). No reader is on this path.
- **vf(0x30)** (slot 6) = `0x359BA0` `xor al,al` (only on handler error, `0x2774A2F`).
- The vtable copy keeps all 15 slots (dump of `0x57260C0`: 0 `1437580`, 1 `3600C0`, 2 `35EA90`,
  3 `1437600`, 4 `35EA90`, 5 `359B50`, 6 `359BA0`, 7 `359B50`, 8 `35EA90`, 9 `1437740`, 10
  `359B50`, 11 `35EA90`, 12 `359BA0`, 13 `359B50`, 14 `3600C0`).
- **Crypto:** sessions 1 and 2 come from the same ctor with the same argument 0
  (`.xtls 0x100B82BF xor edx,edx`; the mod passes 0). So their `CryptogramAesGcm` is identical
  (off). `OnRecvPacket` `0x2773CA6` and the writer `0x2A1FB38` check it the same way.

## 4. Did the Ack go to session 1? No (Q3) [E]

- The target is the TrocParams session (§2), not a global or a user lookup.
- In B2 the handler never ran (§1), so nothing was sent to anyone.
- Even if the handler runs, `value+0x48` = session 2 → `ExecuteTroc` → finder+0x10 = session 2.
- The host's client never received a 2840.

## 5. DER decode `0x4063250` (Q4)

- `0x4063250` = `jmp .xtls 0x14D5F300` (Denuvo; not analysed).
- Call `0x2C492DA`-`0x2C492DC`: `xor ecx,ecx; rdx=&ptr; r8d=len`. **No session pointer is passed**
  [E]. It looks like `d2i(NULL,&p,len)` [S].
- On failure: `0x2C49467` `*res=[0x6CDB9B0]` and nothing else; there is no log on this path.
- The vf2 **then overwrites the result**: `0x2A21A05` `mov [rsi],ebx(0)`. A DER, RNG or RSA
  failure is completely silent, and the session is not closed either (the executor only closes on
  res != 0, `0x2774A11`). The `0x143B450`/`0x143B670` log calls only cover the size check
  (`0x2A21AA4`).

## 6. Minimal fix (Q5)

1. **`build_session`: write 0, not 2**, to `*(u32*)[s2+0x88]` (or leave the ctor's 0, which means
   deleting the line and `kSessionId`).
   - Effect [E]: key 0 skips the tables (`0x143A5A1`) and goes to the common FIFO, exactly like the
     boot login of session 1. The executor checks `0 == 0` (`0x27748D0`) and runs the handler with
     `session = value+0x48` = session 2. The Ack goes `ToTarget(session 2)` → vf9 `session2_send`.
   - Sharing id 0 with session 1 is harmless. Once session 1 has a user, its deferred Req use the
     user key (`0x2774066`-`0x2774071`, `[user+0x58]`). Without a user, every value carries its
     own session pointer (+0x48).
   - What is lost: per-key serialisation for session 2's pre-login Req (only 2319 and 2490, sent
     in order).
2. **Do not use any nonzero id whose bits 28-29 are 0 and whose low 20 bits are ≥ N (1)**. That
   is an out-of-bounds read of the heap, and a nonzero read would be dereferenced as an object.
   Ids 1, 2, 3, … all do this.
   - `0x40000000`/`0x80000000`/`0xC0000000` would use the single real table-0 subqueue. It is
     unclear who else uses it [S], so 0 is preferred.
3. Optional canary: log `*(u32*)[s1+0x88]` at P1. 0 is expected [S]; if it is not 0, copy session
   1's value.
4. After login, user 2's deferred Req use `[user2+0x58]`. Its subqueue is registered by
   `0x2A837E0` in `CreateUser` (D0 §1.3) [E for the registration, S that `+0x58` is the
   registered key].

## 7. Lower priority: hang when quitting to the title after B2

- **Nothing in the server references session 2** apart from the transient finders and
  `TrBufferPoolValue+0x48` [E; D0 §10, and §1 here]. In B2 that value was freed at the drop.
  There is no "close all sessions" loop: `ServerNet+0x18` is the only session pointer.
- **`ServerNet::Stop` `0x2772400` is bounded** [E]:
  - it sets `+0x10A=1`;
  - phase 1, `0x2774F00`: waits for threads `[+0x48]` (stride 0x88, `+0x70` = running) to exit;
    it wakes them by pushing to Q0 (`0x2774F5B`);
  - phase 2, `0x2774FC0`: pushes a "quit" item with key 0 into `ServerNet+0x38` for each deferred
    worker `[+0x50]` (`0x277503B`-`0x2775075`);
  - each phase loops at most 3×20 × `Sleep(3000)` (`0x2772440`-`0x2772467`,
    `0x2772480`-`0x27724A7`). The third round (`esi==2`, force) returns true at once
    (`0x2774FA2`/`0x2774FB8`). So it waits about 2 min at most per phase and does not hang forever;
  - then it frees the queues, including `0x143A500` on `+0x38`.
- **Hypotheses [S], in order:**
  1. The out-of-bounds read at table 0, index 2 read a **nonzero** heap word on that run. Then
     `0x143AB10` locked or pushed into a foreign object, and the common FIFO got `{2, value}`.
     The pop side (`0x143A6F0`/`0x143A9C2` repeats the same out-of-bounds index; it needs
     `[entry+8] == -1`) can leave a worker stuck, or corrupt that object's lock. A worker that
     never exits is then killed (or left) by Stop, and its held lock can freeze whoever waits on it
     later (the title loader).
  2. The mod's own hooks/threads holding a lock that a `TerminateThread`'ed server thread was
     waiting on.
  3. Unrelated to session 2.
- **Recommendation:**
  - Fix 6.1 first; with key 0 there is no out-of-bounds access, so hypothesis 1 disappears.
  - Before the host leaves the world: stop injecting and drop the pointer (`g_session2 = 0`).
    **Do not free** session 2 and do not call its vf3 Close (`0x1437600` → `.xtls 0xB8A9000`:
    the null-user check cannot be verified statically). With no user and no pending value, no
    game code can reach it.
  - Once user 2 exists, a clean logout needs the game's own logout of that user (not analysed).
  - If the hang reproduces with id 0, attach a debugger and take the thread stacks at the hang;
    that cannot be resolved statically.
